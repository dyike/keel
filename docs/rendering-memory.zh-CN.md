# 渲染内存与复用

[English](rendering-memory.md) | 简体中文

组件划分的是状态和布局边界，当前渲染器仍按帧收集绘制指令并写入 drawable。本次上传优化没有实现通用脏区域重绘或滚动像素复用。

## 上传优化解决了什么

在本机 Apple M5 Pro 上，独立的 1×1 Metal 程序仅清屏后约占 97 MiB；加入一次 4 KiB 缓冲复制后约占 154 MiB。增量远大于复制数据，说明提交复制工作会触发额外驱动分配。这确认了触发分配的工作路径，尚未给出私有内核对象名称，也不是所有设备通用的 Metal 内存常量。

应用分阶段采样中，第一个覆盖绘制阶段完成后增加约 156 MiB；禁用路径几何绘制后仍出现。这个命令缓冲还包含上传，当时应用纹理只有约 7 MiB，因此不能把整个增量归因于路径复杂度。

统一内存设备现在直接初始化共享的只读几何缓冲，采样图片的首次完整上传也直接写共享纹理。小型可变 uniform 缓冲保持原路径。CPU 生成完整 mip 链，按 sRGB 解码到线性光空间、过滤后重新编码，alpha 保持线性，不长期保留 CPU 图片副本。原生逐级对照覆盖奇数尺寸，观察到与 Metal mipmap 生成器的最大通道差值为 2/255；两种过滤实现并非逐位相同。

后续或局部图片更新继续走有序 GPU 复制，并在 GPU 上重建完整 mip 链。可变缓冲更新、读回和其他 GPU 复制也保留原路径，这些工作仍可能触发驱动分配。因此本次优化不代表所有应用的进程总上限。非统一内存设备、共享纹理分配失败时回退到原路径。原生自动释放池绑定同一 OS 线程，selector 预先缓存。

本机 CPU mip 链基准约为：96² 的 0.05 ms、256² 的 0.33 ms、1024² 的 5.25 ms。超大图片仍须单独检查响应时间，不能把这些数字推广到任意图片尺寸。

## 脏区域重绘

需要追踪变化绘制操作的新旧边界并取并集，包括裁剪、变换、透明度、图片和选区。布局位移还必须清除旧位置。未知操作、窗口缩放、设备丢失、像素比例变化、背景或清屏状态变化时回退全量绘制。跳过组件布局不能漏掉输入处理。

当前公共 GPU 接口没有 scissor 能力，可通过可选驱动接口增加损伤区域裁剪，其他后端保持全量绘制。背景改为只填充损伤区域，不能清空整个附件。离屏覆盖和透明图层须独立判断失效；窗口坐标下的裁剪不能直接用于图集坐标。

drawable 不一定保存上一帧内容。局部绘制必须先确认原生内容保留契约，再按 drawable 身份记录损伤历史；否则需要自有背景纹理。2920×1898 的一份 RGBA 像素约 21.1 MiB，5016×2820 约 54.0 MiB，均未计对齐。必须先把旧纹理的暂时保留和进程峰值预算算进去。

## 滚动复用

正文不变时，滚动仍改变整个会话视口。可考虑有固定字节预算的分块像素缓存，复用未变消息，只绘制新露出的条带。缓存键须包含稳定消息身份、内容版本、宽度、像素比例、字体/主题版本和绘制效果。选区、hover 只有在混合结果等价时才能拆成独立覆盖层；小数像素移动、变换裁剪和过滤边缘须增加像素测试或回退正常绘制。

预算还要包含飞行中命令保留的资源，不能按每条消息无限分配纹理。缓存未命中或预算耗尽时正常绘制，不降低帧率。复用优先走已有渲染路径；若为了移动像素引入 GPU 复制，可能重新触发本次避开的驱动分配。实现前先对照已有消息虚拟化，核算新增纹理与减少像素绘制的收益。

验收必须在相同像素尺寸的原生窗口中覆盖加载、反复滚动换向、工具流式更新、拖选复制、窗口缩放和静止回收。物理占用峰值、实际呈现帧间隔和 CPU 提交耗时分别报告；保留全量渲染作为像素对照，不能用缩小窗口代替优化。

## 本机应用验证（2026-10-14）

实际安装的 OneCatch 客户端在相同 2920×1898 像素、历史会话和三轮三屏往返滚动下，带呈现计时版本的进程峰值由 364 MiB 降到 304 MiB。移除临时计时后的最终版本为 293 MiB；随后缩小并恢复窗口时累计峰值升到 333 MiB。单次固定尺寸结果不代表稳定全场景低于 300 MiB。

真实滚动、缩放恢复和中文拖选复制通过。实际呈现间隔小于 100 ms 的子集 P50/P95 两版均为 8.33/33.33 ms，但最大间隔由 41.67 ms 变为 91.67 ms，输入时序和样本数不同，不能据此保证尾延迟无回退。尚未实际验证新的流式工具输出和超大图片场景。详细采样和证据路径记录在 OneCatch 的 `docs/keel-memory.md`。本次补丁仍是本地工作区版本。

## 同帧裁剪覆盖复用（2026-10-14）

同一帧里，路径内容、绝对偏移和最终裁剪范围完全相同的覆盖掩码，现在共享图集位置并只栅格化一次。不同父级仍在交集阶段独立合成，不合并最终绘制、不改变透明度和绘制顺序。缓存只是当帧的 CPU 索引，下一帧清空，持续空闲时释放；没有新增 GPU 纹理，也不保留滚动页面的像素。

保留绝对变换输入，避免将整数平移看作等价后改变浮点求值顺序。测试检查不同偏移、裁剪、描边和路径不能共享；24 帧原生 Metal 像素与改动前逐字节一致，覆盖重复/嵌套裁剪、透明度、移动、空闲和回收恢复。100 个重复圆角裁剪的离屏基准，三次中位数从约 1.68 ms/帧到 1.12 ms/帧；这是特定绘制负载，不是实际客户端帧率。

实际安装客户端追踪的一组 5016×2820 帧，路径绘制数累计从 27,185 降到 15,945。同尺寸加载、三轮滚动的呈现计时版本峰值为改前 448 MiB、改后 441 MiB；最终无临时日志版本为 434 MiB，静止约 143 MiB。单轮峰值差异小，不能声称稳定的内存降幅或达到 300 MiB。两组实际呈现样本数明显不同，不足以证明尾延迟无回退。

本轮前段仍在 2920×1898，原版本缩放复测约 345 MiB；解锁后桌面尺寸变化，后段必须单独按 5016×2820 比较，不能与上一节 293 MiB 混算。原尺寸下的最终版缩放峰值尚未完成复验。

整张覆盖图集跨帧复用曾在 114 个客户端帧里零命中，已撤回。提前释放已完成命令缓冲的试验也未证明资源释放收益：原实现完成后已经释放测试纹理。真正的脏区域绘制和滚动像素复用仍未落地，不能把本次同帧去重称为局部重绘。

原生 1×1 清屏试验延长观察后，约 97 MiB 会在无新提交的第二秒降到约 11 MiB，而 Metal 资源统计仍约 0.875 MiB。设置和不设置纹理 volatile 的两组都有回落。这表明本机存在约 86 MiB 绘制相关延迟回收；立即释放对象后的高读数不是永久驻留的证明，也没有找到可在不影响流畅度的前提下强制回收这部分的公开接口。

最小程序的分类快照还确认，未映射图形物理占用从活动时约 85 MiB 降至空闲时 640 KiB，IOAccelerator 映射从约 3 MiB 降到 832 KiB。它定位到驱动图形分类的延迟回收，而非应用纹理大小。

## 毛玻璃闲置回收与包内图标（2026-10-17）

macOS 毛玻璃的独立渲染路径现在会在闲置一秒后释放可重建的 GPU 缓存，缩小备用 drawable 池，由 Core Animation 保留已经显示的完整画面。下一帧申请 drawable 前恢复完整像素尺寸。半浮点线性表面和三重缓冲保持原样。回收与绘制、销毁串行执行，AppKit 不等待渲染锁；连续绘制复用同一个定时器。原生测试覆盖三种材质、完整分辨率恢复、缩放、最小化和提前关闭；合成器截图同时检查闲置后仍能透出背景颜色、保留不透明内容。

开发应用包已经包含多分辨率 ICNS，Keel 不再为这些包重复加载运行时 PNG；显式调用 `SetIcon` 仍能替换图标。Void 同样复用包内图标，普通可执行文件保留 PNG 回退。本机相同 1960×1360 像素的 Void 设置窗口，从改前约 198 MiB 降到最终正常构建的约 72 MiB；仅 GPU 回收的版本约 147 MiB。IOSurface 驻留从 61.6 MiB 降到 20.5 MiB，最终原生 CG Image 分配为 16 KiB，原来为 16 MiB。

最终构建启动峰值为 131 MiB。将实际客户端放大到 5120×2820 像素再恢复，累计峰值达到 620 MiB，回到原尺寸后闲置降至 75 MiB。这证明闲置占用下降，不代表峰值低于 100 MiB；本次没有旧版本对应的大幅缩放对照。开发客户端实际滚轮浏览应用列表时累计峰值为 117 MiB，停下后约 65 MiB；随后打开设置累计峰值为 153 MiB，闲置约 76 MiB。开发包也正确跳过了运行时 PNG 生成。改动来自本地 Keel 工作区和 Void 构建，尚未发布为 Keel 版本。
